# Mezonas: v1 implementation plan

Source of truth for *what* to build: [`ARCHITECTURE.md`](ARCHITECTURE.md) (v0.8). This file says *how* and
*in what order*. It follows the Build plan (ARCHITECTURE §18) milestone by milestone. Each milestone
ends green: `pnpm typecheck && pnpm test` pass and its "done when" check is shown working.

Nothing here adds to the v1 scope in ARCHITECTURE §1. When this plan fills a gap the architecture leaves
open, it says **DECISION**, and the code carries a `// DECISION:` comment at the spot.

Status: **Phase 1 (foundation, local only) built** (§3). Every platform package, `apps/api` and the `apps/web` shells are in, and `pnpm check` passes against local Postgres with `COUNTERSIGN_REQUIRE_DB=1`. The stack runs locally: migrations and seed, `wrangler dev` with the Worker, a real `RunWorkflow` and the cron on local Postgres (`docs/local-development.md`). Not started: cloud (phase 2) and the product screens, tools and use cases (phase 3; Pia and the Materials pack are not built, `packs/materials` is a stub). Stack: the same as Plenary Labs (§1.1). Product shape: ARCHITECTURE v0.8.

## 1. Decisions

### 1.1 Open items from ARCHITECTURE §20

| Item | Decision | Why |
|---|---|---|
| Stack and hosting | **Same as Plenary Labs** (ARCHITECTURE v0.2). `apps/api`: one Hono Worker serving `/api/*`, the built `apps/web` as static assets (`run_worker_first: ["/api/*"]`), the Cloudflare Workflow classes and the cron handler. `apps/web`: React + Vite + React Router. Postgres 16 with pgvector on **Neon** (branches `main` = production, `staging`, plus throwaway `ci-run*` branches per CI run, as in Plenary Labs; environments in `docs/operations.md`). Files in **R2** (Worker binding; S3 API only for signed URLs). Toolchain copied from Plenary Labs: pnpm, TypeScript, Biome, Vitest with `@cloudflare/vitest-pool-workers`. | One stack across projects: same accounts, deploy workflows, runbooks and habits. No Next.js-on-Workers adapter and no second job vendor. Supabase's extras (auth, realtime, storage) are covered by WorkOS, Durable Objects and R2. |
| DB driver from Workers | **Hyperdrive → Neon, with `postgres-js` + Drizzle.** Locally, Hyperdrive's `localConnectionString` points at Docker Postgres. Fallback: Neon's serverless driver in WebSocket `Pool` mode. | `withTenant()` needs interactive transactions (`set_config(..., true)` then queries). Hyperdrive supports them, and Neon's HTTP mode doesn't. Plenary Labs already reaches Neon through Hyperdrive with Drizzle; check `set_config` inside a transaction in the M0 deploy spike. |
| Auth provider | **WorkOS (AuthKit), as in Plenary Labs.** Port its `apps/api/src/identity/` (WorkOS client, AES-GCM sealed session cookie with a 5-minute refresh, provisioning on callback). Identity is the WorkOS user, mapped to `app_user`. A WorkOS organization maps to a `tenant` (`tenant.workos_organization_id`). Roles stay in our `membership` table, so an operator can serve many clients. Behind `packages/auth` with two adapters: `workos` (deployed) and `dev` (local + e2e: seeded users, refused when `NODE_ENV=production`). | Already proven in your stack. Covers what Supabase Auth would add (invites, magic links, client self-serve) plus B2B extras for later (SSO, directory sync, an admin portal per client). |
| Document requests | **Inbox first, routed to an admin.** A `person` step (ask) goes to the client admin's inbox: forward or upload the missing invoice. With Gmail connected (after the MVP) the workflow can also draft an email to the purchaser (approval on). Owner: purchases come from several places (card spend, purchase orders, …), so per-purchaser routing waits until that's designed. | No email leaves without a person. |
| Operating model | **Managed-agents service** (owner, 2026-11-03). One operator (the owner and their team) builds and runs agents for clients from the back office. Agents are built **per client**: reusable ones are **templates**, forked into a client as its own agent, customized for its data and flows, and versioned per client with lineage to the template (ARCHITECTURE v0.6). Clients get a portal and never edit agents. | Every client's data and flows differ, so agents are effectively custom; templates keep that from becoming copy-paste, and lineage lets improvements flow both ways. |
| v1 connectors | **QuickBooks Online and Gmail**, plus upload (owner, 2026-11-03). Gmail: one mailbox per connection (usually a shared `ap@`/`invoices@`), scopes `gmail.readonly`, `gmail.labels`, `gmail.compose`; only messages matching the connection's query are synced (headers, snippet, attachments); bodies fetched on demand; write tools are drafts and labels, each approved. | Email is where most invoices arrive; narrow ingestion keeps the privacy surface small. |
| Embeddings | **Ship without vectors.** `catalog_item.embedding` stays nullable. Candidates come from key attributes plus `pg_trgm`. | §20 says trigram + attributes is enough for v1. Adding a provider later is one tool change. |

### 1.2 Gaps filled while planning

| Topic | Decision |
|---|---|
| IDs (uuid v7) | SQL function `uuid_generate_v7()` (plpgsql) as the column default, so seed scripts, raw SQL and Drizzle all get v7. Postgres 16 has no built-in v7. |
| DB roles and RLS | Same layout as Plenary Labs. **`cs_owner`** (`DIRECT_DATABASE_URL`) owns the database and runs migrations and the seed. **`cs_runtime`** (NOLOGIN; created by the bootstrap workflow or the first migration, whichever runs first, both idempotently) holds every runtime grant. **`cs_worker`** is the Worker's login role: a member of `cs_runtime` only, no `BYPASSRLS`, owns nothing; the Worker, its Workflows and its cron connect as it. `cs_worker` is created **with SQL** (on Neon by `.github/workflows/bootstrap.yml`, locally and in CI by `packages/db/scripts/provision-worker-role.mjs`), never through the Neon console/CLI/API: Neon-managed roles join `neon_superuser` and would skip RLS (Plenary Labs ADR 0002 §15). `scripts/setup-postgres.sh` builds the same roles on a plain Postgres for CI and local work. A test checks effective privileges, inheritance included. (Role names avoid `app_user`, which is a table.) Every tenant table: `enable` + `force row level security`, policy `tenant_id = any(current_setting('app.tenant_ids', true)::uuid[])`. All tenant reads and writes go through `withTenants(ids, tx => …)` (and `withTenant(id, …)` for one), which opens a transaction and runs `set_config('app.tenant_ids', $1, true)`. Client sessions and every run set exactly one id; operator sessions set the clients they serve. Queries also filter by `tenant_id` (§4). |
| Global tables | `tenant` and `app_user` have no `tenant_id` and are read only by `packages/auth` through a narrow owner-side module. **Templates** and shared skills have `tenant_id` null and are visible only in operator sessions (`app.operator = on`, ARCHITECTURE §4). Client agents and client-only skills carry the client's `tenant_id` like any client data. |
| Operator across clients | Back-office sessions carry the set of clients the operator serves (from `membership`); every `/api/ops` request runs inside `withTenants(those ids)`, narrowed by `?client=` when one is selected. Portal sessions carry their one client. The back office has a client switcher; the portal has none. |
| Migrations | `drizzle-kit generate` for tables. Hand-written custom SQL migrations (`drizzle-kit generate --custom`) for extensions, roles, `uuid_generate_v7`, the RLS loop, immutability triggers, and the `item_alias` expression unique index (`coalesce(...)`), which Drizzle can't express. |
| Immutability | One trigger function `forbid_update_except(variadic cols text[])`. Attached to `agent_version`, `skill_version`, `workflow_version` (allow `status`), `raw_record` (allow `is_deleted`) and `doc_extraction` (allow nothing). `DELETE` is blocked on all five. |
| Money | `numeric(14,4)` maps to `string` in Drizzle. `packages/core/money` wraps `decimal.js`. No JS floats for money. |
| Senses outbox | `event` gets one extra column, `dispatched_at timestamptz null`. `emit()` inserts the row inside the caller's transaction. After commit, the Worker dispatches it in `ctx.waitUntil()` (router below) and stamps `dispatched_at`. The cron (every minute) re-dispatches anything undispatched for more than 30 s. Dispatching twice is harmless because run ids are deterministic (next row). |
| Starting runs | One Workflow class, **`RunWorkflow`**, executes any workflow for a client agent. A pure router in `packages/workflows` maps a client's sense event to the enabled workflows in the live version of that client's **active** agents whose trigger `event` and `filter` match. `apps/api` then calls `env.RUN_WORKFLOW.create({ id: runId, params })` for each. **Run ids are deterministic** for triggered runs: uuid v5 of (event id, agent id, workflow slug) for events and of (agent id, workflow slug, scheduled time) for schedules, so a re-dispatch or a repeated cron tick can't start a second run. Manual, command and test runs get a fresh v7. Schedules: the every-minute cron checks each active schedule trigger in the client's timezone (`cron-parser`). // DECISION: v5 for triggered run ids, v7 elsewhere. |
| Waiting on inbox items | The step (a `person` step, or an action that needs approval) creates the inbox item with `run_id`, checks it isn't already resolved, then calls `step.waitForEvent(name, { type: 'inbox-<id without dashes>', timeout })`. `POST /api/inbox/:id/resolve` writes the resolution, then `env.RUN_WORKFLOW.get(runId).sendEvent({ type, payload })`. A timeout throws inside the step; the executor catches it and follows the step's `onTimeout`. If that send fails, the cron re-sends it (§1.5 "Approval resume"). |
| Executor and Workers types | `packages/workflows` runs step lists against a small `StepRunner` interface (`do`, `waitForEvent`, `sleep`) and has no Workers types. `apps/api`'s `RunWorkflow` adapts Cloudflare's `WorkflowStep` to it, the way Plenary Labs' `run-group.ts` passes `step.sleep` in. Unit tests use a fake runner; one Workers-pool test drives the real class. Step outputs stay small (ids and short summaries), because step results have a size limit. A fork evaluates its paths in order and runs the first match; `for_each` runs its steps with the step's `concurrency` (default 10) under names `${stepId}:${index}:${childId}`. |
| Expressions and rules | Fork paths and trigger filters are **rules** (`field op value`, matched all/any), the form the builder shows; they compile to JSONLogic (`json-logic-js`) in `packages/core`. Templates `{{steps.<id>.output.<path>}}` / `{{trigger.<path>}}` / `{{item}}` use a small path resolver in `packages/core`, shared by the builder (field picker, validation) and the executor. No `eval`, no JS. |
| Agents vs `db` | **Agent reasoning reaches business data only through tools.** Inside `packages/agents`, only `src/registry/` (agent, skill and workflow versions) and `src/log/` (step_run, tool_call, external_action) may import `@countersign/db`. Tool handlers live with their owners (platform, connectors, packs). The dependency check enforces this (§2). |
| Seeded and template definitions | Platform templates (`document-clerk`, `coordinator`, `builder`, `supervisor`): bundles in `packages/db/seed/agents/<slug>.v1.json`, inserted once as templates. Pack templates (Pia with her workflows) are inserted as templates when the pack is installed; forking them into a client is a separate step. Everything is validated by its Zod schema (and workflow validation) before insert. The runtime only ever reads version rows. |
| LLM record/replay | `packages/llm` hashes (model, system, messages, tools, tool_choice) into `fixtures/llm/<hash>.json`. `LLM_MODE=replay` is the test default and fails loudly on a miss. `record` calls the API and writes the file. `live` doesn't touch fixtures. |
| Cost | Per-model token price table in `packages/llm/pricing.ts`. Check the numbers against current Anthropic and OpenAI pricing when M4 starts; nothing is hard-coded from memory. |
| Model providers | (owner, 2026-11-04: "use both models") Anthropic and OpenAI. The platform speaks one request shape, the Anthropic Messages format; `packages/llm/src/openai.ts` translates it to OpenAI's Responses API (plain fetch, `store: false`) and the answer back, so the client, `callTool`, the agent runtime, cost and record/replay are provider-blind. A model id names its provider: `openai:<model>` (e.g. `openai:gpt-5.5`) goes to OpenAI, any other id to Anthropic (`routingTransport`). Reasoning is not carried between turns on OpenAI; effort `xhigh`/`max` map to `high`. |
| Extraction input | Send a PDF as a `document` content block (base64) and images as `image` blocks, with `tool_choice` forcing the `record_invoice` tool, whose schema is `InvoiceExtraction` (Zod → JSON Schema). Check page and size limits at M2 and split long PDFs by page if needed. |
| UI | (owner, 2026-11-03) The **Mezonas design system** in `packages/design-system`: `tokens.json` (source of truth, light and dark) and `tokens.css`, component CSS (`ds-*`, `dt-*`, `mz-*`), logos, icons, Geist and Geist Mono (served locally), and the brand book in its README (voice, colour meanings, type, layout). `apps/web` imports its CSS and maps the tokens into the Tailwind theme; screens use token names and component classes, never raw colours. The owner's v1 screens in `docs/design/` remain the layout reference; their Groundwork look is retired. The product is named Mezonas everywhere a person sees it; `countersign` stays the code name. |
| Live updates | **v1 polls.** The run page polls every 2 s while a run is going; the inbox badge and thread view every 15–30 s. Every long job exposes a status the UI can poll. Later upgrade: push over WebSockets from a Durable Object, the way Plenary Labs' `GroupLog` streams sessions. |
| Workflow model | A **structured step list** (owner's design): trigger, then steps run top to bottom; forks hold ordered paths with rules plus otherwise and join afterwards; `for_each` holds nested steps (ARCHITECTURE §10.1). No free-form edges, so validation, execution and merging all walk one tree. // DECISION: an editor session keeps one rolling draft version of the bundle, saved after 2 s of idle editing, so history isn't flooded; publish is what people see in history. |
| Builder | A nested sortable list with `@dnd-kit/core` + `@dnd-kit/sortable`: drag by handle to reorder, into and out of fork paths and `for_each` blocks; keyboard reordering for accessibility. The add-a-step palette and the inspector's forms are generated from skill and tool schemas, so a new skill appears without UI code. Validation runs in the browser on every change (same code as the server). |
| Packs | A pack is a workspace package under `packs/` exporting a `PackManifest` (ARCHITECTURE §12.1), tool handlers, a Drizzle schema and Hono routes. Its tables go in the one migration sequence (drizzle config lists every pack schema). `apps/api` registers packs in one list; installing a pack adds its templates once; enabling it for a client is a row in `tenant_pack` and allows forking its templates there. |
| External actions | Every write to a client's tool is an `external_action`. **Approval is on by default** (§ Step approvals): the action is written `proposed` with an inbox item in the same transaction; approval flips it to `approved`. When a step runs without approval (step `not_required` + connection `auto` + agent mode `act`), it's written `approved` by the system. Execution runs in its own `step.do` keyed by the idempotency key (`<run id>:<step id>:<index>`), so a retried step can't write twice. Connectors capture `before` where the API allows (QBO: read the record with its `SyncToken` first), automatic or not. |
| Operator skills | Written in the back office as a form (name, description, instructions, a tool picker over every registered tool, input/output field editors that produce JSON Schema, settings with an optional `clientSpecific` flag, an optional summary template). Always `agent` mode. No code. Shared by every agent, or written for one client (`tenant_id` set). |
| Role checks | The route contract in `packages/core` declares each route's roles; Hono middleware enforces them and sets `app.tenant_ids` (and `app.operator` for operators). Two contract tests: every `/api/ops` route is operator-only; no portal route's response schema includes an agent bundle, instructions, prompts or cost fields. |
| Connectors in the portal | The operator offers connectors per client (`tenant.settings.connectors_offered`); the client admin signs in to each from the portal's Connections page (provider OAuth; `connection.connected_by` records who). The operator never connects on a client's behalf and never sees credentials. "Remind" emails the client admin a link to the portal page for that connector; it carries no credentials or authority of its own. |
| Permission matrix | `connection.permissions` per verb (`auto` / `approval` / `off`) plus a connector-specific scope; for writes it's a **ceiling** (`auto` = steps may skip approval, not that they do). Defaults: read auto, create and update approval, delete off. The operator sets it in the back office; the client admin can tighten it in the portal (the API refuses loosening from a client role); each change is a `connection_change` row and applies to the next tool call, overriding any step set to skip approval. |
| Step approvals | (owner, 2026-11-03) Every `action` step, and every `skill` step whose tools can write to a client tool, carries `approval: { required: 'required' | 'not_required', approver?, timeout?, onReject }`, **`required` by default**: new steps, forks, Builder drafts and pack templates all start that way. The builder offers switching it off only where the client's connection allows `auto` for that verb; validation refuses `not_required` elsewhere. Approver: the step's, else the agent's, else the client's setting. Steps that only read or only write the platform's own records have no approval setting; a `person` step is the checkpoint for anything else. |
| Email forwarding (MVP) | Cloudflare Email Routing for `EMAIL_FORWARDING_DOMAIN` → the Worker's `email()` handler; one private address per client on its upload connection (`config.forwarding`), plus allowed senders; MIME parsed with `postal-mime`; PDF and image attachments become `document(source='email')`; headers kept, bodies not. Unknown senders are dropped and counted. // DECISION: forwarding is the MVP's email path; the Gmail connector comes after. |
| Requests | `inbox_item(kind='change_request')` in the operator's request queue, with the subject (a service, a run, or none for a new service) and the client's text. Resolution links the client agent or template versions made for it. The Builder can take the request text as an instruction for that client's agent. |
| Bundles and lineage | One `agent_version` holds the whole `AgentBundle` (definition + workflows + settings). Templates and client agents share the `agent` table (`kind`), so versioning, the editor, the builder, test runs and rollback are one code path. Client versions record `based_on_template_version_id`; merges and promotions record `merged_from_version_ids`. Operational fields (bindings, approver, service name, run status) live on the client `agent` row with an append-only `agent_change` log, so rebinding a connection isn't a new version. |
| Diff and three-way merge | Pure functions in `packages/core` (`diffBundles`, `mergeBundles(base, ours, theirs)`), shared by the server and the merge view. Keys: workflows by `slug`, steps and fork paths by `id` (wherever they sit in the tree), skills by `skill`; objects merge field by field; the order of each step list merges as a sequence (an insert keeps its neighbours; two different reorders, or the same step moved to different places, conflict); other arrays and scalars as whole values. Only-one-side changes are taken; identical changes once; otherwise a conflict `{ path, base, ours, theirs }`. The merged bundle must pass workflow validation before it can be saved. Step and path ids are uuids generated once, copied on fork, never regenerated. |
| Updates and promotion | "Update available" = linked client agent whose `based_on_template_version_id` is older than the template's live version. Applying: `mergeBundles(base = client's base template version, ours = client live, theirs = template live)` → merge draft (`author_type='merge'`) with resolutions applied → test run on that client → publish. Promotion runs the same merge into a template draft (base = client's base template version, ours = template live, theirs = client version) with client-specific values stripped: connection ids, record ids in templates and settings marked `clientSpecific` in the skill's settings schema. // DECISION: no automatic updates in v1. |
| Client agent activation | A client agent becomes `active` only with every required connector bound, a live version, and one passing test run on that client since its last publish. Pausing stops new runs; running ones finish. |
| Client run timeline | Each skill and tool may declare a `summary` template over its output (e.g. `Extracted {{lines.length}} lines from {{header.vendor_name}}`); the executor renders it into `step_run.summary`. No summary → the step's client label + status. Model text never reaches the portal except through these templates. |
| Back office and portal in one app | One SPA with two layouts: `/ops/*` (operator) and everything else (portal). The `/ops` bundle, including the workflow builder, is code-split, so client users never download it. Sign-in lands operators in `/ops` and clients in `/`. |
| Sandbox client | Seeded client "Sandbox" with fixture data (vendors, transactions, invoices, price history), used for building, test runs and demos without touching a real client. |
| Gmail sync | Cron every 5 minutes per connection: `users.history.list` from the stored `historyId`, filtered by the connection's query; if the history id has expired, a bounded `messages.list` with the query replaces it. Attachments are stored once per sha256 as `document(source='email')` and linked like uploads, with the sender domain as a vendor signal. // DECISION: poll, not Pub/Sub push, in v1. |
| Page thumbnails (match review) | Render in the browser with pdf.js from the signed R2 URL. No server-side rendering, so no container is needed. |
| Invoices for fixtures | Synthetic invoices that look like normal vendor invoices. Swap in real (redacted) ones later and re-record. |

### 1.3 Decisions made while building `packages/core`

| Topic | Decision |
|---|---|
| Durations | Cloudflare Workflows' own string form (`"30 seconds"`, `"5 days"`, units up to weeks), so the executor passes them to `step.sleep` / `waitForEvent` unchanged. `parseDuration()` gives milliseconds. |
| Budgets | `budgets.maxCostUsd` is a decimal string (default `"0.50"`), not a JS number, because cost is money (invariant 6). |
| External tools | A `ToolSpec` with `sideEffect: 'external'` must name its `connector`; the gate and the publish check find the connection matrix by it. A `none` tool's verb is `read`. |
| Pack templates | `PackManifest.templates` is a list of `{ slug, bundle: AgentBundle }` (whole bundles, the unit v0.6 versions), not separate agent and workflow lists. |
| Trigger payloads | Event triggers carry the event type's payload; manual triggers their declared input; schedule triggers `{ scheduledAt }`; command triggers `{ args }`. |
| Built-in step outputs | `person` → `{ approved, answer, by }`; `fork` → `{ pathId, pathName }` (which path ran); `for_each` → `{ count }`; `wait`, `notify`, `stop` → nothing. |
| Rule operators | `=` / `!=` compare loosely (JSONLogic `==`), so `"5"` from a form equals `5`; `is` is strict (for `true`, `false`, `null`); `contains` is substring or membership; a rule's value that is exactly one `{{ref}}` compares against that field. An empty `all` matches, an empty `any` doesn't; a fork path with no conditions is a validation error. |
| Merge details | Entity keys `skill:<id>`, `workflow:<slug>`, `step:<id>`, `path:<id>`, `otherwise:<id>`; conflict paths `<key>#<JSON pointer>`, `<key>#@exists`, `<key>#@location`, `<list>#@order`. Two inserts at the same spot are both kept, ours first. Deleting an item conflicts with any edit, insert or move-out inside it on the other side, reported once at the topmost deleted item. A move between lists counts as an edit; a reorder within a list doesn't. Unresolved conflicts keep ours so the draft is always complete. |
| Portal field check | The contract test refuses portal response fields named `bundle`, `definition`, `instructions`, `prompt(s)`, `systemPrompt`, `cost`, `costUsd`, `cost_usd`, `modelCost` and token counts; business figures such as `landedCost` are allowed. |
| Workers tests | `apps/api` pins Vitest 4 for `@cloudflare/vitest-pool-workers` (as Plenary Labs does); the rest of the repo is on Vitest 5. |

| Test connector | The testkit connector is registered everywhere except production, so the Sandbox client exercises connections and approvals before any real connector exists. |

| Portal inbox | Client users never see operator-assigned items; a `client_user` sees items assigned to them or to `client_user`; a `client_admin` sees the rest. Payloads are stripped of forbidden fields at any depth. |
| Cron | Each client in its own `withTenant` transaction, over the window (previous minute, this minute]. |
| Event payloads | `packages/senses`' event catalog is the contract for payloads; `packages/agents` emits `inbox.resolved` and `external_action.done/failed` in those shapes through its injected `Emit`. |
| Web | React Router 7, Tailwind v4 mapped onto the Groundwork tokens with Tailwind's own palette removed; `/ops` is a separate lazy chunk loaded only after the operator check; a small `useApi` hook instead of a query library. |
| Local Worker | `pnpm dev` runs `wrangler dev --env-file ../../.env`, so the root `.env` gives the local Hyperdrive connection string. |

### 1.5 Decisions made in Track B

| Topic | Decision |
|---|---|
| Approval resume | Delivery of a resolution to its run is durable. A resolved inbox item with a `run_id` is pending until the run records that it took the resolution (`inbox_item.run_received_at`, written by the executor through `InboxPort.received` after the check before waiting or the event). Resolving sends the event after the commit as before; the every-minute cron re-sends the event of every pending item resolved more than a minute and less than a day ago whose run is still `queued`, `running` or `waiting` (`apps/api/src/runs/resume.ts`). Sending again is safe: each item's event type is waited on at most once, the run checks the item before waiting, and `sendEvent` sends nothing to an instance that has ended. A failed send is logged and retried on the next tick. |
| One `step_run` per step | `step_run (run_id, node_id)` is unique (migration 0003); the executor's step log and the agents runtime's `startStepRun` insert with `on conflict do update` (a no-op that returns the existing id), so a retried step, or a step's failure record, reuses its row. |
| Portal sign-in to a tool | `POST /api/connections/:connector/authorize` (client admin only) connects an **offered** connector. Only connectors that need no provider sign-in (`auth: 'none'`, today the testkit) connect from the portal; OAuth connectors answer 409 `not_available` and the portal shows "Not available yet" until the first OAuth connector brings its callback route and state secret (`canSignIn` in `apps/api/src/routes/portal.ts`). ### 1.20 Approver rules (built, 2026-11-04)

§1.17's approver rules: who approves a change to a client's tool. They decide **who**, never
**whether**: approval-on defaults, the connection matrix and act mode are untouched (invariant 8).

| Topic | Decision |
|---|---|
| Storage | `tenant.settings.approver_rules = {revision, rules}`; every save bumps the revision and writes a `tenant_change` row (`setting: approver_rules`, `side`, the rules `from` and `to`, the reason, the actor). No migration: 0012 stays unused. |
| A rule | `{id, match, approver, setBy, note?}` in `packages/core/src/approvals/rules.ts` (Zod, pure, shared by API, runtime and both editors), at most 50 per client. `match` has any of `connector`, `tool`, `verb` (create, update, delete), `amountOver {value, currency}` and `agentId`; every field given must hold, and a rule with none matches every change. `approver` is the client admin, a role (`client_user`: anyone in the client), one named client user, or the operator on the client's behalf. First match wins. |
| Amounts | A tool that carries money declares where in its input (`ToolSpec.amount {path, currencyPath?, currency?}`, dotted paths; `defineWriteTool({amount})`). The testkit's update declares `amount` in USD; no other connector does yet (QuickBooks' tools will). Amounts are compared with decimal.js, strictly over the threshold, and only in the same currency; an amount without a readable currency, or a tool without `amount`, never matches an amount rule. A JSON number in the input is read through its decimal text. |
| Precedence | The client's rules first, then the step's approver, then the agent's (its definition, then the client agent's override), then the client's default (`approvals.external_actions`), then the client admin. Rules come before every approver an agent names, so a client admin's tightening wins over an operator-set step or agent approver. |
| When it applies | The gate (`packages/agents` `callTool`) reads the rules fresh for every proposal (`RuntimeStore.approvalRouting`, which replaces `clientApprover`), so a tightening applies to the next approval at once, mid-run too. Approvals already waiting keep their assignee. A rule naming a person who has left the client routes to the client admin. |
| Snapshots | A run's `config` keeps the rules it started under (`approverRules`), beside the agent's bindings and approver. Each approval's inbox payload records what routed it: `approverRoute {source: rule, step, agent, client or default, ruleId, revision}`. Who approved is recorded as before (`external_action.approved_by`, `inbox_item.resolved_by`). `mayResolve` is unchanged: an item assigned to a person is theirs alone, not the admin's or the operator's. |
| Person steps | Rules match changes to a client's tool (connector, tool, verb, amount); person steps have none of these and keep their own assignee. |
| Who sets them | The operator, for the clients they serve: `GET/PUT /api/ops/clients/:id/approver-rules` (others 404), any change, with a reason. The client admin: `PUT /api/approver-rules`, stricter only, checked on the server with core's `clientTighteningProblems` (403 `loosening` with the problems). Client users read them (`GET /api/approver-rules`). A save over a newer revision is 409 `stale`; saving nothing new is 409 `no_op`; a rule naming someone who isn't the client's, another client's agent, an unknown connector or write tool, a tool and connector or verb that disagree, or an amount on a tool without one is 422 `invalid_rule`. |
| Stricter only | Strictness: the operator 0, a role (anyone in the client) 1, the client admin or one named person 2. The client admin may raise a rule's approver to the same or a higher level (taking an approval back from the operator, narrowing to the admin or a person, moving between people) and add new rules, anywhere, naming the admin or one person. Never: removing, reordering or re-matching a rule (anyone's), or naming the operator. Because rules come first, a new level-2 rule can only make any change's approver stricter. The server keeps `setBy` and makes ids for new rules. |
| Screens | One editor (`apps/web/src/approvals/ApproverRules.tsx`) for both surfaces, like the matrix. Back office: the client page's "Who approves" section (ordered list, add, edit, up and down, remove, reason, change log, and "Try it with a sample change", which runs core's `routeApproval` over the unsaved rules, the agent's approver and the client's default). Portal: a "Who approves" section on Connections, under the matrix: the client admin picks only the same or a stricter approver per rule and adds rules naming the admin or one person; client users read them. The portal calls the operator's side "we" and never names the operator's people. |

| ElevenLabs | Mezonas' own account (`ELEVENLABS_API_KEY`, `ELEVENLABS_WEBHOOK_SECRET`). | Voice agent settings | From the step in the agent's version (invariant 4): `purpose`, `firstMessage`, `voiceId`, `tools` (read tools) and `maxMinutes` (1–30, default 10) on `call.place` / `call.answer`. | Opening | Fixed in code, in each portal language (marked for review): "this is an automated assistant calling for {client}", then the version's own line, then "May I keep a written record of this call?". |
| Purpose and opening are fixed text (invariant 9) | `purpose` and `firstMessage` become the voice agent's instructions and opening line, so they come only from text written in the step in the agent's version. A tool spec lists such fields in `fixedInputs` (`call.place` and `call.answer` list both). The gate (`callTool`) compares them with the action step's input as written, before templates (`StepContext.literalInput`, set by the executor's action port). It refuses the call before any approval card or write when a field was filled from a template (`{{trigger.*}}`, `{{steps.*.output.*}}`), changed after the step, or written by a model (a skill or agent mode has no step input). This way, what a contact texted or said (read with `message.get` or `call.get`) can never steer a call, including a step set to `not_required`. Workflow validation flags the same thing (`input_not_fixed`: a templated field on an action step, or a skill whose tools include such a tool), so publishing is refused too. Inbound answering reads the step's raw input and forwards or sends to voicemail if a field is templated. Other fields (`to`, `tools`) may still be templates. We chose refusal over quoting the purpose into the prompt as delimited data: refusal holds whichever path filled the field. |
| Re-run of a placed call | When an action left `executing` runs again after a crash, `call.place` returns the call already placed under its key before any consent, opt-out or quiet-hours check, in both `before` and `run`. This means an opt-out since then can't record a call Twilio placed as failed. Every call not yet placed is still checked. |
| At most one call | Twilio's call create takes no idempotency key (NOTES.md). The call's request (`CallRequest`, with the action's key and `requestedAt`) is stored by `prepareOutbound` before Twilio is called, and is the attempt. A re-run that finds a request but no placed call never places again, and skips the checks as above: it lists Twilio's calls from our number to the contact (`GET Calls.json?To=&From=`) and keeps the outbound ones created since the request (two minutes' leeway for clocks) that no other call record has. Exactly one: adopted, recorded under the request's call id so Twilio's webhooks for it find it. None or several: the action fails with "The call to … may have been placed; check before trying again" and the operator gets a `review` inbox item with the candidates (`UnconfirmedWriteError`, as for messages in §1.22). |
| Approval | `call.place` is approved as a whole: the card shows who, why (purpose), from which number, the agent (the item's agent), the tools it may use and the time limit. Consent and opt-out are checked when the card is drawn, and again with quiet hours when the call is placed. A refused call never reaches the inbox. During quiet hours the action fails ("place it again after that"); nothing is queued. |
| Consent | Calls need their own consent channel, `voice` (to the contact's phone). Agreeing to texts isn't agreeing to calls. Changing the phone withdraws it, an opt-out (including STOP) stops calls too, and calling in isn't consent. |
| During the call | The voice agent's server tools are the step's tools that read, and that are also the agent's own tools (extraTools or skills), plus `propose_follow_up`. The tool webhook `POST /api/voice/:tenantId/tools/:tool` needs the call's id and token (HMAC of client and call under a key derived from the webhook secret: no storage), stops working once the transcript has arrived or the time limit plus 5 minutes has passed, and refuses any write whatever the step lists. Then the tool runs through `callTool` (the gate) as the call's client agent version, with its bindings and the connection's matrix. Tool use is kept as `CallToolCall` raw records (a call has no step run of its own). |
| Changes asked for on a call | Never made during the call. `propose_follow_up` notes what was asked. After the call, each note becomes a `review` inbox item for the approver (step, agent, client setting, else the client admin), with the follow-up and the transcript record as sources, and no run (so nothing resumes or re-sends). A person makes the change. |
| Inbound calls | `POST /api/twilio/:tenantId/voice`. The client agent's answering step is the first active client agent bound to this Twilio connection with a live workflow on `call.received` whose steps include `call.answer` (oldest agent first). It answers live only when `decideToolCall` says the step runs without approval: the step is `not_required`, the matrix allows `auto` for create, and the agent is in `act` mode (invariant 8). ElevenLabs must also be set up. Otherwise the call is forwarded to the operator's forward number, or goes to voicemail. The decision and its reason are stored with the call and written in the contact's thread, then `call.received` carries them. In the run that starts, `call.answer` records the answer once, automatically; if the agent didn't answer, its before-state check fails with the reason, so no approval card is drawn after the fact. A retried ring answers the same way without deciding again. If ElevenLabs fails while the call rings, the caller still reaches voicemail. |
| Voicemail and forward | Voicemail is a polite greeting in the client's language, a tone, up to 2 minutes (`<Record>`), stored once as `CallRecording`. Forward is `<Dial>` to the operator-set number for 20 seconds. Neither is an agent's usage. Playing voicemails in the portal isn't built. |
| After the call | ElevenLabs' post-call webhook (`/api/elevenlabs/post-call`) is checked by its signature with a 30-minute window. It is matched to our call by `call_id`/`tenant_id` dynamic variables and the voice agent's id, and stored once per conversation. The transcript and summary are untrusted data (tool results only, through `call.get`), kept only if the person said yes to a record (`record_ok` data collection). Otherwise nothing of what was said is kept. No audio is kept (`record_voice: false`). A line goes in the contact's thread, and `call.completed` is emitted. Calls the voice agent never spoke on (voicemail, forward, no answer, busy, failed) are completed from Twilio's final status. |
| Usage | `usage_daily.call_seconds` += Twilio's `CallDuration` of each finished call an agent placed or answered, once (the final status is stored once first), for that client agent, by UTC day. The rollup leaves it alone. |
| Setup (operator only) | `/api/ops/clients/:id/calls`. Turn calls on (our voice webhook URLs stored in `connection.config.voice`), take a number's calls (sets its `VoiceUrl` and `StatusCallback` at Twilio), set the forward number, see who answers now (the same check) and the recent calls. Every change goes to `connection_change`. Turning calls off clears the numbers first. The Calls panel is on the client's Texts and WhatsApp page. |
| Isolation | Every webhook's path names the client and scopes the lookup (`withTenant`). Twilio's signature uses that client's subaccount token, and the tool token is bound to the client and the call. Another client's path gets 403 or 401. |
| Network inside a transaction | The voice webhooks call ElevenLabs (make the agent, hand the call over) inside the request's one `withTenant` transaction, within Twilio's ~15-second answer window. This is accepted to keep one connection per request; it is a follow-up if it holds connections too long. |
| Not built | Recording audio, playing voicemails, answering-machine detection, transfer to a person mid-call, deleting unused ElevenLabs agents, choosing the voice agent's LLM, SHAKEN/STIR and CNAM registration (Twilio console), numbers outside the US, translation of transcripts (§1.18 next step). |

### 1.24 Decisions made in stream J (Stripe billing)

> **Superseded in part by §1.32 (2026-11-05):** Mezonas now works out each bill and Stripe only
> bills it. The subscription, base quantity, meter, usage report, price-id and subscription-webhook
> rows below no longer apply; credits, unit costs, rounding, periods, collection and secrets still do.

Owner, 2026-11-04 (§1.17): each client is a Stripe customer; a monthly base fee per active client agent includes an allowance of credits; usage beyond it is billed per credit; one credit is one cent of what the work cost us (model cost plus provider costs), converted with unit costs kept as operator settings; the markup is in the overage price. migration 0009 (its own PR, #34).

| Topic | Decision |
|---|---|
| Where the records live | A client's Stripe ids (customer, subscription, the base and overage items), the base quantity Stripe has, the subscription status and the last invoice's outcome are in `tenant.settings.billing` (identifiers, no money). The tenant table is global, so the webhook finds a client by customer id without a client scope; updates merge into the key in one statement (`jsonb_set`). What can't go there is in migration 0009. Per client, with forced RLS: `billing_usage_report` holds one row per client, period and day, with money as `numeric(14,4)` plus currency; only status, error and sent_at change, and rows are never deleted. Also per client: `billing_event`, which stores each Stripe event once. Global, read by every session and written only when `app.operator` is on: `billing_setting` (one row) and `billing_unit_cost`. |
| Settings | All placeholders until the owner sets prices. Allowance: 2,000 credits per active agent ($20 of our cost). Unit costs: 1.0000 per USD of `cost_usd`, 0.0083 per message, 0.1000 per 60 call seconds. Meter event name: `mezonas_credits`. Invoices due in 30 days. No Stripe price ids yet. The operator edits them in `/ops/billing`. When the price ids are saved they are checked against Stripe: the base price must be licensed and monthly, the overage price metered and monthly, both in the same currency. Their amounts are kept as snapshots for the screens. Without a Stripe key, the ids are saved unchecked and no amounts are shown. |
| Credit conversion | Generic over measures: a measure is a `usage_daily` column (by its SQL name), and the unit cost setting for that name prices it (`unit_cost` per `per_units`). Every column except the key is a measure. A column a later migration adds (`messages`, `call_seconds` from the texts and calls branches) counts as soon as the Drizzle schema has it and a unit cost exists. No code names a measure. Tested with a `widgets` column added to the test database. |
| Rounding | Credits are integers. A client's day is priced across all its agents and measures, then rounded up once to whole cents (any work at all is at least one credit). The period's credits are the sum of its days. Everything is decimal.js; nothing passes through a float. |
| Allowance | Pooled across a client's agents: per-agent allowance × active client agents when the day is reported. Overage is the credits beyond it. Each report sends only the increment over what was reported earlier in the period, never a negative one: an allowance that grows mid-period (a new agent) takes nothing back. |
| Active agents | Client agents with run status `active` (not paused, retired, drafts, discarded or test copies). A paused agent is not billed until it is activated again (open for the owner). |
| Periods | Calendar months in UTC, like `usage_daily`'s days. Subscriptions are anchored to midnight UTC on the 1st of next month (`billing_cycle_anchor`, prorated first invoice), so Stripe's periods match ours. |
| Collection | `collection_method=send_invoice` with `days_until_due` from the settings. Stripe emails the invoice with its hosted page. v1 has no card-on-file flow. |
| Quantity | The base item's quantity is kept equal to the client's active agents. After activate, pause and retire (deferred until after the response), and on the hourly pass as a safety net. It is set as an absolute value, so a repeat or a race lands on the same number. Changes prorate. |
| Usage reporting | On the cron's hourly pass at the usage sweep's minute (:07 UTC, after the rollup). Per client set up for billing: sync the quantity, report yesterday (UTC), then retry unsent reports from the last 30 days. Steps: (1) insert the day's row (`pending`, or `none` with nothing to send) with identifier `mezonas:<tenant>:<period>:<day>`; (2) send a Stripe billing meter event under that identifier, which is also the Idempotency-Key, timestamped at the day's last second; (3) mark the row sent or failed. A day already reported sends nothing new. A pending or failed row is resent under the same identifier. Usage that changes after its day is reported is caught by the next day's increment. The day after a month ends reports that month's last day at 00:07 UTC (Stripe's grace period is to check, NOTES.md). |
| Test runs | `usage_daily` includes test runs of a client's agents, so they are billed to that client. A template's Sandbox test copies are in the Sandbox client, which is not billed. Open for the owner. |
| Webhook | `POST /api/billing/stripe/webhook`, public. The `Stripe-Signature` header (HMAC-SHA256 over `t.payload`) is checked on the raw body with a 300-second tolerance in both directions, then the event is parsed with Zod. Handled: `invoice.paid`, `invoice.payment_failed`, `customer.subscription.updated`, `customer.subscription.deleted`. The client is found by customer id. Each event is stored once per event id (a repeat answers `duplicate`). A subscription event older than the last one applied changes nothing. Other events, and customers we don't bill, are acknowledged and dropped. Bodies over 256 KB are refused. |
| Stripe client | `packages/connectors/src/stripe/`: form-encoded requests, injected `FetchLike`, Zod on responses, `StripeError`. No connector manifest and no agent tools: billing is Mezonas' own infrastructure. `fakeStripe` is in `@countersign/connectors/testing`. What could not be checked against Stripe's docs (blocked here) is in its `NOTES.md`. No `Stripe-Version` is sent, so the account default applies (open). |
| Back office | `/ops/billing` (sidebar: Billing) shows each client's period so far (agents, base fee, credits used, allowance, extra, our cost, billing status) with a Set up button, and the settings form (allowance, days until due, price ids, meter event name, unit costs per measure; a priced measure the rollup doesn't have yet says so). The client page has a Billing section: set up with an optional billing email, the plan and our cost, the credit meter, Sync now, this period's daily reports and the invoices with links. Routes: `GET /api/ops/billing`, `PUT /api/ops/billing/settings`, `GET /api/ops/billing/clients/:id`, `POST …/setup`, `POST …/sync`, all operator-only (the contract test covers the 403s). |
| Portal | `/billing`, for the client admin only (`GET /api/billing`, `client_admin`), shows: the plan (services × base fee, the monthly total), credits included each month (shared by its services), extra credits and their price, this period's credits as a meter, a notice when the last payment failed, and Stripe's invoices with the hosted page ("View and pay" while open) and PDF. Never our cost, tokens or prompts. Credits are the billing unit, so the field names avoid the forbidden list (`creditsUsed`, `extraCredits`, `extraCreditPrice`). The contract test and a test that walks the response keys check this. Strings are plain English for stream I to convert. |
| Secrets | `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` are Worker secrets (`docs/operations.md`), empty in `.env.example`. With no key, billing is off: the cron skips it, set-up answers 409, and the screens say Stripe isn't connected. |


### 1.25 Reach out: agents contacting people (owner, 2026-11-04; design)

An agent knows the people it works with and reaches out to them by email, text, WhatsApp or call, in their language, under conditions the operator sets. Builds on contacts (§1.22), calls (§1.23), approver rules (§1.20) and languages (§1.18).

| Topic | Design |
|---|---|
| Contacts | §1.22's contact gains: **email**, **preferred channels in order** (e.g. WhatsApp, then call), **language** (already there), **timezone** and quiet hours (default: the client's), **roles** (labels such as `purchaser`, `owner`, `vendor rep`), consent **per channel** (email added beside texts, WhatsApp and calls), and notes. Client data: per client only (invariant 1); the operator and the client admin edit them. |
| An agent's people | A template declares the **roles** it reaches (`people: [{role, description, required, channels}]` in the bundle, no contact data). A client agent **binds each role to one or more contacts**, like connection bindings: operational data on the client agent, never in a version, so forks and promotions never carry anyone's details (invariant 11). Activation refuses a required role with nobody bound. This is how "add people to an agent's memory" works: who they are, how to reach them and when. |
| Conditions | Per binding, checked in code before anything is sent: **urgency → channels** (default: urgent: call, then text; normal: the contact's preferred order; FYI: email only), **hours** (the contact's timezone and quiet hours; urgent may be allowed outside them only if the operator says so), **how often** (at most N per day and one open reach-out per contact and subject), **only if** (an optional rule over the step's facts, the same rules as forks, e.g. amount over $500), and **escalation** (no reply after a set time → the next channel; stop at the first reply, an opt-out or the last channel). |
| The skill | `comms.reach-out`, built in. Input: `to` (a role or a contact), `about` (the record it concerns, as sources), `purpose` (fixed text, §1.23's fixed-input rule), `message` (a fixed template per language, or "compose": the model writes it from the fixed purpose and the record's data, in the contact's language), `urgency`, `expectReply`, `timeout`. Output: `outcome` (`replied`, `no_reply`, `declined`, `opted_out`, `not_allowed`), the channel used, the reply as untrusted data, the contact, and sources. |
| Waiting for a reply | The step waits like a person step: the run waits for the reply event (`message.received`, `call.completed`, an email reply) or the timeout, using the same wait the inbox uses; escalation steps happen inside the wait. The workflow then forks on `outcome`. |
| Channel choice | The contact's preferred order, filtered by the binding's allowed channels, consent, what the client has connected and the hours; the first that passes is used; none passes → `not_allowed`, recorded with the reason, nothing sent. |
| Language | The contact's language, else the client's, else English. Fixed templates carry one text per language (as summaries do, §1.18); composed messages are written in that language. Replies in another language are translated when §1.18's message translation lands. |
| Approval | On by default (invariant 8). One approval covers **the reach-out plan**: who, why, which channels and how many attempts; each attempt inside the plan then runs. Approver rules (§1.20) route these approvals like any other change. A step runs without approval only under the usual three conditions. |
| Evidence and safety | Every attempt and reply goes in the contact's thread with the run, the agent version and the sources (invariant 10). Replies and transcripts are data, never instructions (invariant 9). Consent, opt-out, hours and caps are code, not model judgement. Test runs never send. |
| The agent's own channels (owner, 2026-11-04) | An agent is **given channels**, as it is given connections: each client agent binds an email channel, a texting number, a WhatsApp number and a calling number, each to a connection. Email can be **a mailbox of its own** (a Gmail account made for the agent, which the client or the operator signs in to), **Mezonas' sending service** (Resend, from an address on the client's verified domain, our domain until then), or **a person's Gmail** that the person signs in to and lets the agent send from. Texts and calls use the client's Twilio numbers (§1.22, §1.23). The skill sends only through the agent's bound channels; an unbound channel is `not_allowed`. |
| Email sending | Gmail gains send (`gmail.send`, Google's send scope, behind approval like every send; this adds to the Gmail app review) and still never syncs beyond the connection's query (invariant 12). A `resend` connector is Mezonas' infrastructure: a domain per client verified by DNS records shown in the back office. Replies come back to the client's forwarding address (§1.6) or the Gmail mailbox and are matched to the reach-out by thread and headers; reply text is untrusted data. |
| Who edits (owner, 2026-11-04) | **The operator and the client admin, fully**: both add and edit contacts, bind people to an agent's roles and set or loosen the conditions (hours, how often, urgency → channels, escalation, "only if"). Every change is logged with who (the tenant_change pattern). What stays the operator's alone: whether a step needs approval and the connection matrix (invariant 8), and binding channels to connections. Consent and opt-outs are never overridden by either. |

#### Decisions made while building phase 4 (2026-11-05)

Human release (ARCHITECTURE §6.9 "Human release"; the row "Human release" above). Built on `claude/access-release-migration` (migration 0013, `access_release`, chained after phase 3's 0012) and `claude/access-release`.

| The code | Six digits by rejection sampling from `crypto.getRandomValues`. ### 1.32 Billing statements: Mezonas works out the bill, Stripe bills it (owner, 2026-11-05)

Owner, 2026-11-05: "switch to us and we can do all the different parts internally, not in stripe".
Each agent has its own monthly price, set in Mezonas. Stripe only holds customers and invoices. It
sends each invoice, takes payment and tells us the outcome. There are no Stripe products, prices,
subscriptions or meters. **This supersedes §1.24's subscription, quantity, meter, price-id and
webhook decisions.** Credits stay as §1.24 has them: one credit is one cent of our cost, from unit
costs over `usage_daily`, each day rounded up. Migration 0016 is in its own PR (#72). All amounts
are USD, `numeric(14,4)` with a currency, and decimal.js in code.

| Topic | Decision |
|---|---|
| Where prices live | `billing_template_price` holds a template's monthly price and included credits. It is global like `billing_unit_cost`: every session reads it and only operator sessions write it. It is edited on the template's Settings tab and listed on `/ops/billing`. `billing_agent_price` holds a client agent's override, per client with forced RLS. Each override has a required note and records who set it and when. It is edited on the client agent's Settings tab. Every change to either table is written to `agent_change`, the agent's audit log (with `tenant_id` null for a template). `billing_setting` gains `default_agent_price`, `credit_price` and `auto_send`. `allowance_credits_per_agent` becomes the default included credits, since it means the same thing. The Stripe price ids, meter name and price snapshots stay in the table, unused. // DECISION |
| Placeholders | Default agent price $250.0000 a month with 2,000 credits. An extra credit costs $0.0200. Auto-send is off. Invoices are due in 30 days. No template has a price until the operator sets one. |
| Which price | The override applies first. Then the template's price, then the platform rule, then the defaults. The platform rule: a client agent forked from the **supervisor** template (`slug = supervisor`, `tenant_id` null, `SUPERVISOR_SLUG`) costs $0 and includes 0 credits. The supervisor is how platform agents reach a client (§1.28), and it is identified by its template. A price the operator sets on the supervisor template overrides the rule. An agent with no template (blank or copied) uses the defaults. Only USD prices are saved. // DECISION |
| Agent days | On the hourly cron pass at the usage sweep's minute (:07 UTC), each client set up for billing gets one `billing_agent_day` row per active client agent for today (UTC). An active client agent is `kind = client`, not a test copy, `status = active` and `run_status = active`. Each row snapshots the agent's name (service name, else agent name), its price, its credits and where the price came from. The insert is `on conflict do nothing`, so the first price seen that day sticks. The rows are never updated or deleted. A day counts if the agent was active at any hourly pass. Paused and retired days are not billed. Activating, pausing and retiring no longer call Stripe. // DECISION |
| Building | Each :07 pass builds the statement for the month just ended for every billing client that doesn't have one yet. That is normally on the 1st, after the rollup. A pass that failed is caught up an hour later. Building is idempotent: one statement per client and month (unique key). A client set up after the month ended gets no statement for it. Usage counts from the day the client was set up (`setUpAt`), so work done before billing is not charged. With auto-send on, a new statement is sent right after it is built. With it off, the statement waits as a draft. // DECISION |
| Agent lines | There is one line per agent, described by its name from the last billed day. The amount is the sum of the agent's daily prices ÷ the days in the month, rounded half up to cents once per line. A price change mid-month therefore prorates each price by its own days, and an agent active for 10 of 30 days pays a third. A zero-price line shows as "Included". |
| Extra usage | One "Extra usage" line on every statement: max(0, credits used − pooled allowance) × the credit price, rounded half up to cents. The pooled allowance is the sum, over each agent's billed days, of its credits ÷ the days in the month, rounded half up to whole credits once. The credit price is the one in the settings when the statement is built, and the statement keeps it. // DECISION |
| Test runs | Usage by test copies is excluded: template test runs run as test copies, which are separate agents (§1.5, §1.16). Open for the owner (separating them needs a column on `usage_daily`). |
| Adjustments | The operator can add adjustments to a draft whose send hasn't started: a description of up to 200 characters and an amount in whole cents, positive or negative, never zero. Adjustments can also be removed then. The statement's total is recomputed each time. A database trigger enforces this: lines can't be inserted, changed or removed once Stripe has the invoice, except that each line's Stripe invoice item id is set once. A statement whose total is negative can't be sent (422). |
| Statuses | `draft` → `sent` → `paid` / `payment_failed` / `void`. A statement whose total is zero is `nothing_due` and never goes to Stripe. That covers a zero total at build time, and a draft adjusted to zero, which becomes `nothing_due` when it is sent. `void` and `nothing_due` are final, and nothing goes back to `draft` (trigger). The operator can void a draft only while its send hasn't started. Once Stripe has it, a void happens in Stripe and comes back through the webhook. // DECISION |
| Sending | There are four steps. Each stores Stripe's id as soon as it comes back, and each has the Idempotency-Key `mezonas:<statement id>:<step>[:<line id>]`. Sending again resumes at the first step not done. With auto-send on, the hourly pass also resumes any draft whose send has started. If the Worker dies mid-request, the retry replays the same answers through the idempotency keys. // DECISION |
| Set-up | Setting up creates the Stripe customer, with the key `mezonas-customer-<tenant>` and an optional billing email. ## 5. Things to verify, not assume

- Intuit API details (M9) and Google's Gmail and verification rules (M10), see those milestones.
- Anthropic: PDF input limits, the tool-use output format with `tool_choice`, and current model prices (M2/M4). Model ids come from agent definitions, with defaults in §2 of the architecture.
- Cloudflare Workflows (the deploy spike): `waitForEvent` event-type naming rules and maximum timeout (the 5-day doc request must fit); whether an event sent just before the wait starts is kept or lost (the check-before-wait in §1.2 covers the common case); `create` refusing a used instance id; step result size and step count limits; testing waits in `@cloudflare/vitest-pool-workers`. Plenary Labs uses `step.do` and `step.sleep` but not `waitForEvent`, so this part is new.
- Neon + Hyperdrive: `cs_worker` created with SQL on Neon, `force row level security`, and that Hyperdrive's transaction pooling keeps `set_config(..., true)` inside the transaction (session-level settings would leak between requests).
- A Workflow step making a long Claude call (30–90 s) completes. Workers limit CPU time, not time spent waiting on I/O (Plenary Labs' ADR 0001 relies on this too).

## 6. Risks

| Risk | Mitigation |
|---|---|
| Extraction accuracy on messy scans | Totals validation routes failures to review; re-extraction inserts new rows; goldens catch regressions. |
| Matcher false positives (the costly error) | Hard-rule veto on key attributes; precision gate in CI; auto-threshold set per agent version. |
| The builder grows into a project of its own | Scope is fixed by ARCHITECTURE §10.5 and the owner's design; a structured list is far simpler than a node canvas; forms and the palette come from schemas, not hand-built per skill; Pia's workflows are seeded as data, so M8 doesn't wait on builder polish. |
| An automatic write does something unwanted in a client's system | Writes default to approval and delete is off; only the operator loosens a matrix and the client can tighten it at any time; every write records its before state and the run that made it; actions show in the run view and the portal timeline. |
| Generic platform, nothing finished | Every milestone ends with something runnable; M8 (Pia) is the proof that the platform is enough to build a real agent; nothing in `packages/*` may special-case a pack (layering check). |
| A write to a client's system goes wrong | Every external write is approved by a person, idempotent, records the prior state, and fails on a stale `SyncToken`; test runs never write. |
| RLS bypassed by connecting as owner | The Worker only has `cs_worker`; a test asserts `current_user` isn't the owner in the request path. |
| Workflows' wait semantics differ from this plan | Checked in the M0 deploy spike, before the executor is built on them. The executor only sees `StepRunner`, so a change stays in `apps/api`. |
| QBO app approval delays | Upload connector is the demo path; M9 runs only against the sandbox. |
| Google verification for Gmail's restricted scopes takes weeks, or testing-mode tokens expire after 7 days | Start the Google app verification as soon as M10 begins, in parallel with the build; for Workspace clients, domain-wide delegation granted by their admin avoids it; upload and QBO attachments cover the demo meanwhile. |
| A malicious email steers an agent | Email text only ever reaches a model inside tool results; Gmail writes are drafts and labels, each approved; ingestion is limited to the connection's query. |
| The operator becomes the bottleneck | Templates mean a client agent starts from proven work; template updates reach every linked client as one review each; the back office ranks what needs attention across clients; the Builder drafts from requests. |
| A bad version reaches every client | Template publishes change no client; each client's update is a reviewed merge with a test run on that client; rollback is per client. |
| Merges lose or garble a client's customizations | Merge is pure, deterministic and covered by golden cases; conflicts are never auto-resolved; the merged workflows must validate; the merge draft is test-run before publish; the previous version stays one click away. |
| Forks drift until templates stop helping | The template page shows customizations and versions behind for every client; promotion folds good client changes back; detaching is explicit. |
| Client data or learning leaks across clients | RLS on `app.tenant_ids` with tests for client and operator sessions; memory and learned records are per client; runs set exactly one client. |
